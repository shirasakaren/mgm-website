# Testing & Verification

**Rule: nothing is "done" until it's been seen working in a real browser.** The established workflow is Playwright (screenshots + interaction scripts) against the dev server, followed by `open http://localhost:3000` for a human look. The dev server must stay running at all times (`pnpm dev:web`); check with `curl -s -o /dev/null -w "%{http_code}" http://localhost:3000` before and after changes.

## Playwright methodology (proven patterns from this codebase)

- **SSR / flash checks**: a browser context with `javaScriptEnabled: false` shows exactly what server HTML renders, used to prove the nav menu's reload-flash fix (nothing of the closed panel may be visible pre-hydration).
- **Computed styles**: sample `getComputedStyle(el).transform/opacity` before/after interactions to verify GSAP end states, for example confirming the Our Work panel actually moved (it had silently no-op'd once).
- **Animation-timing races**: drive `page.mouse.move()` directly (no `hover()` sugar) to hit precise mid-animation windows, for example hovering a Core Competencies card immediately after the section scrolls into view.
- **Stress tests**: repeat a race repro many times (12× single-card, then 4 cards × 5 timing windows × many runs). The Core Competencies race only showed intermittently; a single pass proves nothing.
- **Emulation**: `reducedMotion: "reduce"` (all reduced-motion paths: mount state, hover/unhover swaps, no snap-to-hovered on mount) and `colorScheme: "dark"` (menu text visibility was a real bug once).
- **Viewport matrix** for the no-scroll menu: 1280×800, 1440×900, 1280×600, mobile 390×844, with the menu open: verify no scrollbar and nothing clipped.
- **`reducedMotion: "reduce"` is required for a `fullPage` screenshot to mean anything on this codebase, not just a nice-to-have.** Every `fadeUpOnScroll`-driven section (which is most of the page, on most pages) starts at `opacity: 0` and only reveals on an actual scroll crossing. A `fullPage` screenshot taken without emulating reduced motion captures the page in whatever mid-animation state it happened to be in, which on a first pass can look like "half the homepage is blank" and isn't a real bug at all. Confirmed the hard way during the mobile-responsive audit: an entire first round of ~84 screenshots had to be thrown out and recaptured with `reducedMotion: "reduce"` for this reason. It has a second benefit specific to this codebase: `ScrollSmoother` (see `docs/animation-system.md`) is never created under reduced motion, so it also removes the transform-wrapper interference that otherwise breaks a plain `document.body.scrollWidth` overflow check. On the homepage it also gives a still page: the magnets rest at home with no thrown entrance, the reel shows its finished state with no pin and no autoplay, the compact hero shows its poster, and the footer finale skips its celebration.
- **Per-element overflow probe, not just `document.body.scrollWidth`**, when hunting for horizontal-scroll bugs: comparing `scrollWidth` to `clientWidth` tells you _that_ something overflows but not _what_. A `getBoundingClientRect()` sweep over every element, filtered to `rect.right > viewportWidth`, sorted by overflow amount, finds the actual offending element in one pass, but expect noise from elements deliberately clipped by an ancestor's `overflow-hidden` (this design system uses full-bleed decorative shapes that spill past their own container on purpose); a genuine bug still needs the `scrollWidth > clientWidth` check to confirm it's not just clipped.
- **A closed-form "scroll to the bottom" beats a fixed number of `mouse.wheel()` calls** when scripting repeated page visits: a fixed iteration count can silently under-scroll (smooth-scroll CSS, animation timing, or simply not enough iterations for an unexpectedly tall page all cause this) and produces false "stuck/invisible content" reports that are actually just "the script didn't scroll far enough to see it." Poll `window.scrollTo(0, document.documentElement.scrollHeight - clientHeight)` in a loop until the resulting `scrollY` stops advancing, rather than looping a fixed number of times.
- **Scripted navigation fuzzing catches intermittent bugs a single manual click-through won't.** For "sometimes X breaks" reports (an uncaught exception on some navigations, content occasionally stuck invisible), a Playwright script that repeatedly clicks real `<a href>` navigation links across every route in random order, with a random pre-navigation scroll amount, while listening for `page.on("pageerror", ...)`, reproduced a crash that a first, smaller run (51 navigations) caught only once, confirming a fix needs re-running at a larger scale (100+ navigations) before trusting a "0 repros" result. A fix suspected of interacting with animation timing should always be validated this way rather than by feel.

## Checking the static build

The dev server renders pages on demand; the deployed site is the static export. Anything touching data, routes, media or asset paths must also be checked against the build:

```sh
pnpm build                  # writes apps/web/out (and copies visible papers)
pnpm --filter web preview   # serves out/ on http://localhost:3001, next to the dev server
```

- Walk the key routes (`/`, `/about`, `/projects`, a project, `/articles`, an article, `/publications`, a publication, `/member`, a profile, `/research`, an initiative) and listen for `pageerror`, failed responses and images with `naturalWidth === 0`. Expect zero.
- Articles: `?q=` and `?category=` in the URL, typing into the search field, and the infinite list all run over `/articles-index.json` in the browser; compare result counts for a few queries with what you expect from `content/articles.json`.
- On Windows, the build writes the router's segment prefetch files as nested folders (`__next.about/__PAGE__.txt`), so a local preview logs 404s for `__next.*.__PAGE__.txt` requests. That is a Next export path-separator bug on Windows only; the Linux build in CI is correct (`docs/static-site.md`).
- To test under a sub-path the way a GitHub Pages project URL serves it, build with `NEXT_PUBLIC_BASE_PATH=/mgm-website` and serve `out/` under that prefix: every asset must still load (a missing `withBasePath` shows up as a 404 at the root).

WebGL notes still apply: headless Chromium renders WebGL through SwiftShader, and the articles world rejects software renderers, so headless runs see the DOM list. Check the WebGL world and the projects cover stage with a Chromium launched with GPU flags (`--enable-gpu --ignore-gpu-blocklist`, plus `--use-angle=metal` on macOS). `docs/articles-page.md` lists what to watch.

## Type & lint gates

`pnpm typecheck` (`next typegen && tsc --noEmit`) and `pnpm lint` (eslint) must be clean before declaring done. The Pages workflow runs the typecheck and the build on every PR; there is no unit test suite.

## Commit & push

One discrete change per commit, pushed to a branch with a PR to `main`. The PR's workflow run (typecheck + build) is the final check; watch it with `gh run watch`. Merging to `main` deploys to GitHub Pages, so merge only when the user explicitly asks.
